How this report gets its data

Each build target is measured from the same resource-detection processor package, with only the detector build tags changed between runs. The default build is the baseline; every trimmed build is compared against that same baseline.

Dependency inventory

For each target, the report asks Go for the non-standard packages reachable from processor/resourcedetectionprocessor under that target’s build tags, then rolls those packages up to their owning modules:

go list -deps -tags '<build tags>' \ -f '{{if .Module}}{{.Module.Path}}{{end}}' . | sort -u

The red/green diff is a set comparison: modules present in the default build but absent from the trimmed build are removed; modules still present in the trimmed build are kept.

Published command and builder-config evidence is path-normalized to replace workstation-specific absolute paths with named placeholders. The report run directory retains the exact generated artifacts.

Binary and metadata checks

  1. Each target is built as a collector binary with the same stripped linker flags, so binary size comparisons are measured on like-for-like artifacts.
  2. Detector registration evidence is checked after compilation to confirm selected detectors are present and unselected detector symbols are absent.
  3. Per-module tooltip details come from the same dependency walk, plus the local Go module cache when source size is available.

The report is static HTML with embedded measurements, so it can be opened directly from the run directory.

Categories in the diff view are display heuristics; the underlying data is a flat, sorted module list.
