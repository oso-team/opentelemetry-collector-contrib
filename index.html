A custom Collector using can carry libraries for detectors it never enables. That can mean more , license reviews, and maintenance.

This report presents real measurements from a working implementation of the proposal to make resource detectors independently selectable. can keep the detectors they need and omit libraries used only by detectors they leave out, reducing reachable Go modules and binary size. This is opt-in; users who do not request a trimmed build keep the existing default behavior.

They are compile-time switches: when a tag excludes a registration file, Go omits that detector's runtime implementation and imports before compilation. The approach follows Prometheus's established service-discovery pattern.

The working implementation is organized as four reviewable changes. Chapters 1 and 2 remove hidden dependency edges. Chapter 3 adds build-tagged detector registration. Chapter 4 moves always-compiled configuration into light packages, finally allowing unused SDKs to fall out of custom builds.

    How the comparison is measured
    
    
    Every custom build uses the same source version and build settings. Only the selected resource
      detectors change. The ordinary build with every detector is the 
      used for every comparison.
    

    
    
      
    
        
    Measuring reachable dependencies
    
        
    A Go  is a directory of source code;
          a Go  is a versioned collection of
          packages. For each build, the report asks Go which non-standard-library packages are reachable from the
          resource-detection processor, then groups those packages by their owning modules:
    
        
    go list -deps -tags '<build tags>' \
  -f '{{if .Module}}{{.Module.Path}}{{end}}' . | sort -u
    
        
    The detailed comparison is a set difference. A module is “removed” when it is reachable in the default build
          but not in the selected custom build. A module is “kept” when both builds still reach it.
    
        
    Published command and builder-config evidence is path-normalized to replace workstation-specific absolute
          paths with named placeholders. The report run directory retains the exact generated artifacts.
